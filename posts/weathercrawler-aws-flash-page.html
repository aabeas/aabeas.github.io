WeatherCrawler — a flash-test game for AWS deployments

Date Posted: August 13, 2026

Description: A single-file cloud-init script that stands up a tiny weather-driven browser game on EC2 — built to quickly sanity-check AWS deployments, and a look at what I'd tighten up before it sticks around.

Topics: AWS, Bash, Systems, Security

I needed a fast, disposable way to confirm an AWS deployment path actually worked — instance launches, user-data runs, a service comes up, port 80 answers. Rather than spin up a placeholder "Hello World" page, I built something I'd actually enjoy poking at: a tiny browser game called WeatherCrawler that pulls real weather for wherever the instance happens to be running.

The whole thing is one bash script passed in as EC2 user-data. No provisioning tool, no image build step, no external package beyond what yum/apt already know about.

What it does

On first boot, the script:

  1. Installs python3, curl, and jq — whichever package manager the AMI has.
  2. Figures out where the instance actually is by resolving its public IP and geolocating it: 
    PIP=$(curl -sf https://checkip.amazonaws.com)
GEO=$(curl -sf "https://ipapi.co/${PIP}/json/")
LAT=$(echo "$GEO" | jq -r '.latitude')
LON=$(echo "$GEO" | jq -r '.longitude')
    If either call fails — no egress, rate-limited, offline test environment — it falls back to a small hardcoded list of cities and picks one at random, so the script never blocks on a flaky network call.
  3. Pulls live conditions for that location from Open-Meteo (temperature, precipitation chance, cloud cover, wind speed) — no API key required.
  4. Writes two payloads to disk: a gzip+base64-encoded static HTML page (the game itself) and a ~20-line stdlib-only Python HTTP server that serves it.
  5. Registers the server as a systemd unit so it survives reboots and restarts on crash: 
    [Service]
Type=simple
ExecStart=/usr/bin/python3 /opt/wg/server.py
WorkingDirectory=/opt/wg
Restart=always
RestartSec=5
EnvironmentFile=/opt/wg/env
  6. Opens port 80 on the local firewall and starts the service.

The Python server has exactly two routes: / serves the decompressed HTML, and /weather returns the boot-time-fetched conditions for the instance's own geolocated city as JSON, read out of environment variables the boot script set.

The game — a hex-grid crawler where you navigate from a start tile to an exit, collecting coins — actually maps live weather onto the board:

  • Precipitation sets puddle density and slip chance — step on a puddle in a downpour and you've got roughly even odds of losing a turn.
  • Cloud cover shrinks your visible radius; dense cloud plays like fog-of-war.
  • Temperature controls move speed (colder = slower reactions), and below freezing, frost tiles spread across the board over time.
  • Wind has a chance to randomly deflect your move to an adjacent direction — the higher the speed, the higher the chance.

On load — and on every reset — the page picks a random city from its own hardcoded list and fetches current conditions for that city directly from Open-Meteo, in the browser, no server involved. The EC2 instance's own geolocated weather (the /weather endpoint above) is only used as a fallback if that direct browser call times out. So the game you get is rarely "wherever this EC2 instance happens to be" — it's a new city, and a freshly generated board, almost every round.

Why this shape

The point wasn't the game — it was having something concrete and fast to point at after a deploy. A single script that either produces a working, checkably-alive port 80 endpoint or fails loudly in /var/log/wg-init.log is a much better smoke test than staring at "instance state: running" and hoping. It's also just more fun to demo than a static "it works" page.

What I'd change before it sticks around

This was built for a quick, disposable check, and it shows. Before I'd trust it as anything longer-lived than a demo:

  • Don't run it as root. The systemd unit has no User= directive, so the Python process — and anything that ever went wrong in it — runs as root by default. A dedicated service user costs one line.
  • The OS firewall isn't the real gate. firewall-cmd opens port 80 locally, but the AWS security group is the actual perimeter and this script doesn't touch it. Worth calling out explicitly in any deploy doc so it's not mistaken for "the port is handled."
  • No verification step. If python3 is missing on an unexpected AMI, or the service crash-loops, the only signal is systemctl status wg. A final curl -sf http://localhost/weather with a pass/fail echo into the log would close that gap for free.
  • Base64-encoding the server script hurts editability. It's compact, but every tweak means re-encoding. A heredoc — like the one already used for the systemd unit — would be just as self-contained and far easier to maintain.

Could this run without a cloud provider? GitHub Pages, for instance

Almost trivially — closer than I expected. GitHub Pages only serves static files, so there's no room for the Python /weather endpoint or the server-side IP geolocation step. But it turns out most of the game doesn't need either: it already calls Open-Meteo directly from the browser for every city it rolls, and the local /weather endpoint only exists as a fallback for when that direct call fails. Drop that fallback branch (it just degrades to hardcoded defaults if omitted, same as today), pull the systemd unit and the Python server entirely, and push the HTML to a gh-pages branch. The only real functionality lost is opening on the visitor's own city rather than a random one from the built-in list — a small, optional addition via navigator.geolocation or a CORS-friendly IP-geo API, not a rebuild. For a project whose entire surface area is one HTML file, that's arguably a better fit than EC2 was in the first place — unless the actual goal, like mine, was testing the AWS deployment path itself.
